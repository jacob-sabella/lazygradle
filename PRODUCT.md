## Users

Terminal-native JVM developers (tmux, vim/nvim, shell-first) who want to drive Gradle without opening an IDE. Many of them move between several Gradle repos or services in one day. Both groups matter equally. The typical user already knows Gradle, wants tasks found and run quickly, and wants to read the build output without leaving the terminal.

## Product Purpose

lazygradle is a keyboard-driven TUI for browsing, running, and reviewing Gradle tasks across multiple projects, with live streaming output. It exists to replace the loop of `./gradlew tasks`, grepping, shell history, and scrolling terminal output. Success means a user can find a task, run or re-run it with the right parameters, and inspect the result in a few keystrokes.

## Positioning

lazygradle is to Gradle what lazygit and lazydocker are to their tools. It has four strengths, all confirmed as core:

- **Discoverability:** fast search over large task lists, so nobody has to memorize task names.
- **Repeatability:** saved run configurations (CLI args and env vars) and task history make re-runs one keystroke.
- **Output review:** a dedicated Task Manager with vim-style navigation, visual selection, and yank. Reading output here beats scrolling a terminal.
- **Lightweight and keyboard-first:** starts instantly, needs no IDE and no mouse.

## Operating Context

- Runs inside the developer's own terminal emulator, often alongside an editor in tmux or split panes.
- Works against local Gradle projects. It prefers the project's `./gradlew` and falls back to `gradle` on `PATH`.
- Commands run in background threads and stream stdout/stderr live, so the UI stays responsive during long builds.
- State persists in `~/.config/lazygradle/gradle_cache.json`: projects, task history, saved configurations, theme, and output settings.
- Distributed on PyPI (`pip install lazygradle`) under the MIT license. Requires Python 3.13+.

## Capabilities and Constraints

- Multi-project chooser with cached task metadata. It checks `gradlew` permissions and offers to fix them.
- Current Setup tab: task search (`/`), task details, run (`r`), run with parameters (`R`), refresh (`F5`).
- Task Manager tab: run history with re-run, plus a structured output viewer (`j/k`, `gg/G`, `Ctrl+d/u`, `v`, `y`/`yy`, `+`/`-` zoom).
- Global: number keys switch tabs, `p` opens projects, `Ctrl+h/j/k/l` or `Ctrl+Arrow` moves between panes, and the command palette holds a contextual keys guide.
- The UI is designed and checked at 100x30 as its practical floor. The code no longer enforces a minimum size, and 100x30 is not a confirmed durable product constraint.
- Terminology: "Current Setup", "Task Manager", "Task Output", "saved configuration", "project chooser".

## Product Principles

1. **Keystrokes over clicks.** Every workflow completes from the keyboard. The mouse is optional and never required.
2. **Recall beats memory.** The tool remembers projects, tasks, parameters, and history so the user doesn't have to.
3. **Output is a first-class surface.** Build output is for reading, navigating, and copying, not just scrolling past.
4. **Stay light.** Instant start, no IDE weight, and no feature that slows the core find, run, and review loop.
5. **Familiar to lazy-tool users.** Conventions from lazygit and lazydocker come before novel interaction models.

## Accessibility & Inclusion

- Every Textual theme, light or dark, must stay legible. UI work may not rely on colors that break under any built-in theme, so it uses theme variables (`$primary`, `$surface`, etc.) instead of hard-coded colors.
- Vim and arrow parity: every vim-style binding keeps an arrow-key or standard-key equivalent.
